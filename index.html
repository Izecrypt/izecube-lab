The protocol layer #

An agent is only as good as the documentation it reads. I run a fleet of agents that build, ship and operate products, so I write docs for a reader that executes them literally.

The fleet's shared memory is a Markdown vault with a written protocol: how to retrieve, who owns which note, when a new note may exist, and how to reconcile conflicting facts. Every repo carries an AGENTS.md that agents read before touching code.

What that taught me about documentation

  • Prerequisites must be explicit. An agent will not guess what you assumed.
  • Ambiguity is a failure mode, not a style issue. It shows up as a wrong action, not a confused reader.
  • Recovery guidance is part of the doc. If a step can fail, the next line has to say what to do.
  • One owner per fact. Update the note that owns the fact instead of writing a second copy.
  • Write the failure down. Otherwise the next agent, or person, repeats it.

A real agent doc #

This is a working file, not a showpiece: the AGENTS.md from SignBridge, the sign-language translator I built in nine days. Below are six lines from it, verbatim, with what each one is there to prevent. The annotations are mine.

Line in the fileWhat it prevents
Read Architecture-essentials.md first, Architecture.md and PRD.md as needed.An agent starting work with no context, or reading everything and burning its window. Sets a reading order.
Verification also requires real webcam landmark extraction and Muse calls with a valid local key before claiming an end-to-end demo is verified."Done" claimed after imports and unit tests pass. Defines what verified means.
API keys come from environment variables (MUSE_API_KEY, MUSE_BASE_URL); .env is gitignored and must never be committed.Guessed variable names and committed secrets. Names the exact variables.
Never claim interpreter replacement in any copy or code comment.Overclaiming in generated text. Bounds what the agent may say, not only what it may do.
Fingerspelling fallback for out-of-vocabulary signs is a required feature, not optional.An agent trimming scope. Resolves a priority conflict ahead of time.
All remote API calls go through api/muse.js.Scattered network calls. One chokepoint to test and audit.

Other contracts, same repo-root convention: near-tag (a worker contract with hard rules, an order of work and a handback format) and switch-ops-room (three agent roles and a standup script).

How this page is tested #

Documentation that makes checkable claims should be checked. Two things are done to this page.

1. A link and anchor checker

A stdlib-only Python script fetches every external link on this page and in llms.txt and confirms every in-page anchor resolves. It exits non-zero on any failure, so it can run in CI. X and LinkedIn block bots, so those are reported as skipped instead of failed.

shell
git clone https://github.com/Izecrypt/izecube-lab.git
cd izecube-lab
python3 scripts/check_links.py

ExpectOne line per link, then a summary like 24 external links, 13 anchors, 0 failed.

If it failsA FAIL line names the URL and status code. Fix the link or the claim that depends on it.

2. A cold-read agent test (Nov 19, 2026)

I gave a fresh, small model (Claude Haiku) only this page and llms.txt and asked 12 factual questions. Three were traps whose honest answer is "not stated": my location, relevant experience with a specific database vendor, and product revenue.
